    `WorkspaceIntegrity` (public static, namespace `AzureDesignStudio.Workspace`): enums `IntegrityDepth` (`Quick`, `Full`) and `IntegrityAccess` (`LiveFile`, `Snapshot`); enum `IntegrityOutcome` (`Ok`, `Corrupt`, `Inconclusive`, `Missing`); public sealed record `IntegrityResult(IntegrityOutcome Outcome, IReadOnlyList<string> Problems)`; `Check(string path, IntegrityDepth depth = Quick, IntegrityAccess access = LiveFile)`. A missing file is `Missing`. `LiveFile` access opens `Mode=ReadWrite;Pooling=False` (never create; a read-write open lets a leftover WAL recover, which a read-only connection cannot do - opening the live file read-only after a crash would misreport a healthy file); `Snapshot` access opens `Mode=ReadOnly;Pooling=False` (backups and restore candidates must not be altered). Run `PRAGMA quick_check` or `PRAGMA integrity_check`; the single row `ok` is `Ok`, anything else is `Corrupt` with the rows as problems. A zero-length main file with a non-empty `<path>-wal` is `Corrupt` ("zero-length database with a write-ahead log"); a zero-length file without a WAL is `Ok` (a valid empty database). Classify exceptions through an internal `IntegrityCodes.IsInconclusive(int primaryCode)` that is true for the codes that say nothing about file content - busy 5, locked 6, nomem 7, readonly 8, perm 3, ioerr 10, full 13, cantopen 14 - mapping those to `Inconclusive`; every other `SqliteException` (notably corrupt 11 and not-a-database 26, plus unknown codes) is `Corrupt`. Document in the class summary that this narrows the CONTEXT entry "treat any exception from quick_check as corruption" so a second process holding the file can never cause a healthy workspace to be quarantined, and that quick_check does not verify UNIQUE constraints or that index content matches table content (restore verification uses `Full`).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workspace file -> backup/quarantine code | Tenant inventory, designs and plans are copied into new files on disk |
| file system -> retention code | Deletion decisions are made from file names in a user-writable directory |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-14 | Tampering (SQL injection) | `VACUUM INTO` target path | high | mitigate | The path is always a bound parameter; the test uses a directory name with an apostrophe; no concatenated SQL in `WorkspaceBackup` |
| T-04-15 | Information Disclosure | Backups contain tenant inventory and designs in plaintext | medium | mitigate | Directory 0700 and files 0600 on Unix, profile ACL on Windows, never a shared or temp location; plaintext-at-rest is stated in the runbook (plan 04-12) exactly as for the live database |
| T-04-16 | Tampering / Elevation | Path traversal or deletion outside the backups directory through crafted file names | high | mitigate | Strict anchored name pattern (no separators can match); full-path containment check before every delete; manual backups never pruned |
| T-04-17 | Denial of service / data loss | Healthy workspace misclassified as corrupt because another process held it | high | mitigate | Contention, permission and IO codes are `Inconclusive`, never `Corrupt`; live-file checks open read-write so a leftover WAL recovers instead of failing; only corrupt/not-a-database/unknown codes and the WAL-without-database state are `Corrupt` |
| T-04-18 | Tampering (integrity) | Interrupted backup leaves a truncated file that looks valid | medium | mitigate | Written to a temp name, integrity-checked, hashed, then renamed with no overwrite; an existing target is refused |
| T-04-SC | Tampering | NuGet installs | high | accept | No package is added in this plan (BCL `SHA256`, existing `Microsoft.Data.Sqlite`) |
</threat_model>
