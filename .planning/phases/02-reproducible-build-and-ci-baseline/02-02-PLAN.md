## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nuget.org → lock file → CI restore | the lock must be the authority, not the feed |
| developer global package cache → "clean clone" claim | a warm cache can make an incomplete lock look complete |
| workflow file → merge gate | the guard is the only thing standing between a missing lock file and a green PR |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Repudiation | locked restore / lock-file guard | high | mitigate | Three assertions, not one: NU1004 from `--locked-mode` on drift, `git status --porcelain` for created/rewritten files (`git diff` ignores untracked), and tracked-count equality for a project with no lock at all. Both failure modes are proven negatively in Task 2 before the gate is believed. |
| T-02-06 | Tampering | dependency substitution via a stale lock | high | mitigate | The CI cache key is the lock-file hash (`cache-dependency-path: '**/packages.lock.json'`), so a cache entry from a different graph is not reused; `RestoreLockedMode` is a command-line flag and cannot be dropped by editing props. |
| T-02-07 | Repudiation | "clean clone builds" claim | high | mitigate | The proof runs in a `git clone` with `NUGET_PACKAGES` pointing at an empty directory, and the SDK version, lock-file count, build log, and suite line are recorded. A warm cache or a worktree is explicitly disallowed. |
| T-02-SC | Tampering | package installs | high | accept | No package is added, removed, or version-changed in the repository. The probe runs `dotnet add package` only inside a detached worktree that is deleted, and the clone restores exactly the committed lock files. |
