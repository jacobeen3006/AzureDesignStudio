<objective>
Store guardrail policies per tenant scope on both databases through a legacy-safe migration, and make every enforcement path judge a plan against the policy of the caller's own scope.

Purpose: Success Criterion 4, first half, for policies (IDA-05). Today every authenticated user reads and overwrites one global row, and enforcement reads that row.

Decisions implemented:
- D-09 (one-way, settled in CONTEXT): a nullable tenant column on the guardrail rows added through a Phase 4 style migration on both databases; the legacy Id=1 NULL-tenant row is retained as the inherited default.
- D-05 (settled): the default policy mode is replace (a scope's own policy replaces the inherited default); plan 05-07 adds the per-tenant mode setting and the merge alternative on top of this plan's loader.
- D-14, D-17: the scope key is tid for organizational tokens and oid for personal-account tokens, delivered through the UserState caller.
- D-15 (decided autonomously): guardrail policy changes and tenant setting changes are audited in an append-only AdsSecurityEvents table; this plan creates the table, plan 05-06 writes the policy event, plan 05-07 the setting events.
- D-18: tests run on the in-memory contexts and AdsServerFactory.

Output: tenant-scoped storage with the TenantGuardrails migration on both providers, scope-keyed Get and Set, scope-aware enforcement, isolation tests and a SQL Server container proof.
</objective>

| T-05-10 | Tampering / information disclosure | Cross-tenant read or overwrite of a policy | high | mitigate | Rows keyed by caller.ScopeId with a filtered unique index; the request never names a tenant; TenantIsolationTests prove two tenants and two personal accounts are isolated |
