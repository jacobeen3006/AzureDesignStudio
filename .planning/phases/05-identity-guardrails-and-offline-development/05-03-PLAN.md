<objective>
Only the right role inside the right tenant can read or change the guardrail policy, and every enforcement path judges a plan against the policy of the caller's own scope.

Purpose: Success Criterion 4, first half (IDA-04, and IDA-05 for policies). Today any authenticated user reads and overwrites one global row.

Decisions implemented:
- D-01 (costly, settled): a personal Microsoft account administers its own single-user scope without an app role; organizational tenants need Guardrail.Admin.
- D-04 (costly, settled): the single-user Desktop host implies Guardrail.Admin.
- D-09 (one-way, settled in CONTEXT): a nullable tenant column on the guardrail rows added through a Phase 4 style migration on both databases; the legacy Id=1 NULL-tenant row is retained as the inherited default.
- D-14, D-17: the scope key is tid for organizational tokens and oid for personal-account tokens, delivered through the UserState caller.
- D-15 (decided autonomously): guardrail policy changes and tenant setting changes are audited in an append-only AdsSecurityEvents table.
- D-18: tests run on AdsServerFactory and the extended test auth handler.

Output: role gate, tenant-scoped storage with the TenantGuardrails migration on both providers, scope-aware enforcement, audit events, isolation tests and a SQL Server container proof.
</objective>
