<objective>
Give every request one trustworthy, typed caller: user id, tenant, tenant scope key and roles, derived from the validated principal in one pure place, proved end to end through one RPC, with the single-user host marker and the test helpers every later plan of the phase writes its callers with.

Purpose: the foundation of Success Criteria 1 and 2 (IDA-01, IDA-02). Plan 05-02 puts the same caller in front of the remaining 19 call sites; every other plan of the phase stands on the types and helpers created here.

Decisions implemented (CONTEXT.md; ids assigned by this phase's planning):
- D-04 (costly): the single-user Desktop host is declared by a UserState marker, never by claims; it implies Guardrail.Admin, Deploy.Approver and self-approval; a personal-account scope implies Deploy.Approver.
- D-08 (costly): AdsIdentity.TryFrom accepts the mapped oid and the legacy URI claim through Guid.TryParse, validates tid the same way, never uses sub, never flips MapInboundClaims, and answers with an in-band typed 401.
- D-11 (decided autonomously, supersedes the earlier Server/Auth placement): AdsIdentity lives in the Services project so DeployService and the Desktop in-process host can read it.
- D-12 (decided autonomously): the 401 reuses the services' existing in-band convention (status in the response message); no proto field is added.
- D-14 (decided autonomously): the tenant reaches the services through the same UserState caller mechanism.
- D-17 (decided autonomously): scope key is tid for organizational tokens and the user's oid for personal-account tokens.
- D-18 (decided autonomously): tests run on the Phase 3 AdsServerFactory with a test auth handler that can emit chosen claims.

Output: AdsIdentity and AdsCaller, ServiceTools.TryGetCaller, GetSaved converted as the tracer, the in-process marker, extended test helpers, and the identity test classes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bearer token -> validated principal | JwtBearer and Microsoft.Identity.Web validate signature, issuer, audience and scope before any service code runs |
| principal -> AdsIdentity | The services accept only claims of the validated principal; nothing in a request message names a user or tenant |
| host -> services (UserState) | The in-process Desktop invoker is the only code that may declare a single-user host |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Spoofing | AdsIdentity.TryFrom claim reading | high | mitigate | Identity comes only from the validated principal; the subject claim is never read; two spellings that disagree are refused; empty GUIDs are refused; AdsIdentityTests pins each case |
| T-05-03 | Elevation of privilege | Single-user marker forged through a claim, header or request field | high | mitigate | The marker lives in UserState, set only by InProcessServerCallContext; no claim type can carry it; a test shows a server call reports IsSingleUserHost false and a string "true" does not count; plan 05-10 adds a source guard that the key is never referenced under the Server project |
| T-05-04 | Repudiation / information disclosure | Failure text and audit principal text | low | mitigate | Failure strings never contain claim values or tokens; the principal text is truncated to the audit column width |
| T-05-05 | Elevation of privilege | Personal-account users colliding in one tenant scope | high | mitigate | ScopeId is the oid for the personal-account tenant; AdsIdentityTests assert it and later plans test two personal callers for isolation |
| T-05-SC | Tampering | npm/pip/cargo installs | high | accept | No package is added by this plan (identity code uses System.Security.Claims only) |
</threat_model>
