<objective>
Make plan approvals and decommission approvals tenant-scoped: no scope can approve another's preview, overwrite another's approval, or consume another's token.

Purpose: Success Criterion 4, second half (IDA-05). Today the approval key is the plan hash alone and `ApprovePlan` removes and replaces any existing row, so one caller can overwrite another's approval of an identical plan.

Decisions implemented:
- D-07 (costly, settled): the gate entry and the approval row record RequestedByUserId and scope. (The rule that uses them is plan 05-07.)
- D-09 (one-way, settled in CONTEXT): a tenant column on the approval rows added through a Phase 4 style migration on both databases.
- D-16 (decided autonomously): legacy pending approvals are backfilled with the empty-GUID scope so they fail closed.
- D-17: the scope key is tid for organizational tokens and oid for personal-account tokens.
- D-06 (settled): decommission approvals are tenant-scoped too.

Output: scope-aware gate, composite approval keys with the TenantApprovals migration on both providers, scope-keyed approval flows, isolation and fail-closed tests, and a SQL Server container proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller -> approval rows | A request carries a plan or execution hash; the scope and author come from the validated principal |
| in-memory preview gate -> approval | The gate decides which preview a caller may approve or consume |
| application -> SQL Server / deploy.db | A primary-key rebuild and a backfill run on user data at startup |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-05-22 | Tampering | Overwriting another scope's approval with an identical plan or execution hash | high | mitigate | Composite keys (TenantId, hash); every lookup and write uses the caller's scope; TenantIsolationTests show two scopes coexist |
| T-05-23 | Elevation of privilege | Legacy pending approvals honored in a real scope after the migration | medium | mitigate | Backfilled with the empty-GUID scope, which no caller can have (oid and tid are refused when empty); a fail-closed test; documented consequence: re-approve |
| T-05-24 | Tampering | Data loss or a failed key rebuild on a legacy database | high | mitigate | Guarded batch-by-batch T-SQL looking the old key up by name, no default left behind, premigration backup on Desktop, backup and restore rollback on the server, container proof of upgrade, parity with fresh and with the model |
| T-05-25 | Elevation of privilege / information disclosure | A preview, plan hash or token from another scope approved or consumed | high | mitigate | Gate entries carry the scope; the scope-aware peek and consume return stale for any other scope without revealing existence |
| T-05-26 | Repudiation | An approval row that does not say who requested the reviewed change | medium | mitigate | RequestedByUserId recorded from the gate entry |
| T-05-SC | Tampering | npm/pip/cargo installs | high | accept | No package is added by this plan |
</threat_model>
